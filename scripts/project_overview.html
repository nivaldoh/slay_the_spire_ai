Slay the Spire 1

Turn-based · Ironclad · Ascension 0
  1. 01 / Windows → WSL Read the game

    CommunicationMod sends JSON through a TCP relay.

  2. 02 / Public boundary Build legal choices

    Filter the state and label the cards, targets and screen choices.

  3. 03 / Controller Choose an action

    The model reads the state, recent choices and its persistent notes.

  4. 04 / WSL → Windows Validate and send

    Check the choice belongs to this decision; send its engine command.

↳ The game responds, then the loop repeats. One fresh game process per run. A forced single choice skips the model call.

Total War: WARHAMMER III

Real time · Custom battles · Unpaused at 1×
  1. 01 / Windows → WSL Read the battlefield

    A custom Lua mod exchanges observations and orders through JSON files.

  2. 02 / Public boundary Filter the observation

    Keep friendly units, visible enemies and the lobby roster; remove scoring-only state.

  3. 03 / Controller Decide orders

    A model, scripted policy, skill commander or scripted team controls the army.

  4. 04 / WSL → Windows Validate and acknowledge

    Check the orders; Lua applies or refuses them and reports when.

↳ The battle keeps moving while the model thinks. Delay and order feedback reach the next decision. One launch per job; later battles use rematch.

src/spire/

Whole-run decisions and the earlier first-combat experiments share one engine bridge.

Full runs main Spire track

fullrun/play.py owns the run loop. decisions.py defines public choices; fullrun/llm.py renders prompts, maintains memory and parses replies.

Prompt and enemy rules live in configs/llm/. This is prompt and memory development; playing a run does not train weights.

Engine connection all Spire tracks

engine/runtime.py checks the pinned game and mods and prepares the launch. windows_relay.py relays CommunicationMod to bridge.py in WSL. A bridge error ends the session; there is no reconnect.

Read-only doctor · Protocol and runtime facts

  • combat/: seeded first-combat rollouts, suites, catalogs and evidence audits. Declarations live in configs/suites/.
  • ppo/: actor-critic learning and a budgeted, resumable PPO runner.
  • language/: local Qwen LoRA demonstrations, supervised training, evaluation and REINFORCE.

Game-specific

Battle setup and loop launch → episodes → rematch

CLI entry point · Running comparisons

Controllers several ways to command one army
  • controllers.py selects policies, rotates models and loads outside Python controllers.
  • llm.py: llm and llm_rules issue direct model orders with different prompts.
  • commander.py assigns tasks asynchronously; skills.py executes them.
  • scripted.py: hold and nearest-target baselines.
  • team.py: two scripted members own separate units and progress independently. Model-team work is tracked in Branches.

Read-only doctor · Engine facts

Shared foundation

src/gameai/

Code both games import. This package never imports a game package; the game loops stay separate.

Runtime, model calls and provenance shared mechanics

windows.py holds runtime locks and owns launches. windows_game.py is the Windows supervisor: controller exit or a hard limit ends the game process.

llm.py handles Responses requests, reservations and retries. providers.py declares OpenAI/OpenRouter routing, supported settings and price ceilings.

ledger.py keeps append-only spend totals with hard caps. Each game and provider has its own ledger; the OpenRouter allowance spans both games.

provenance.py records source fingerprints, checks committed code and writes JSON atomically. sft.py builds training datasets from either game's exports.

Choosing a starting point: change model behavior in the game's controller and prompt; change the game connection in its engine/ or Lua mod; change shared mechanics in gameai/. Run orchestration, observations and policy logic have separate roles.

Supporting folders and everyday commands

configs/ and scripts/: prompts, scenarios, suite declarations and experiment tools. Scripts handle queues, inventories, audits, training drivers and this overview.

docs/: state.md holds current work and pending decisions; owner-direction.md records directions. Each track's guide explains its contract; logs and result registers keep the history and evidence.

tests/: component and recorded-engine checks, grouped by package. runs/: local raw evidence and generated artifacts; a clone does not include those experiments.

03 / Prepare training

Export without replaying

Each game's exporter reads saved traces. gameai.sft builds filtered chat datasets with provenance, provider rules and held-out groups kept separate.

Captured data should also support future RL. Training and serving still need more work; a successful dataset smoke check does not show a learning gain.

Spire export · WH3 export · Dataset builder · Plan and limits

Evidence has limits. Only engine-confirmed endings are gameplay outcomes. A component test, a replay or a single battle does not establish policy strength.

Correctness checks and rules for making changes

Verification: only owner-agreed repeatable methods count as verified at their passing revisions. Agreed methods are the reference. New checks remain proposed until agreed.

Tests: tests/ covers protocols, controllers and failures; WH3 includes real Lua components. Use focused uv run --locked pytest -ra … and uv run --locked ruff check .. Markdown links have their own check.

Source stability: play jobs require committed code in their source scope and stop before their next run or episode if it changes. Use a worktree while a job runs. First-combat tools use a broader scope.

Runtime and money: one game controller across both games, unpaused WH3 at 1×. A play command refuses a missing ledger; caps apply to cumulative spend. Commands and constraints.
