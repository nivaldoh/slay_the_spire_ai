# Modding Total War Warhammer III for an LLM battle player

Prepared for Nivaldo Tokuda
8 October 2026

## Start with one small battle

Build a small Lua mod that reads a battle and accepts unit orders from a Python program. Let the Python program handle the LLM, memory, logs, and experiments. Your first useful result is an LLM controlling a few units against the normal game AI on an existing map.

This guide assumes Steam on Windows, a coding agent that can access your PC's files, and structured observations and commands. These are starting choices, not requirements. Your Python and data engineering experience should transfer well to the harness; the unfamiliar part is learning how the game loads scripts and exposes battle objects.

The research supports this starting path. WH3 documents battle scripting, unit control, time manipulation, and a restart command. It does not establish a ready-made, deterministic training simulator. The code and workflow here still need testing in your installed game. [1, 8, 9, 11]

Read Sections 1 through 5 to begin. Use Sections 6 through 9 when the first mod works. Memory, evaluation, and training come afterward. Appendix A is a prompt you can give to your coding agent.

## 1 The few modding concepts you need

| Term | Meaning for this project |
| --- | --- |
| Pack file | A .pack container holding the files your mod adds or changes. |
| RPFM | Rusted PackFile Manager. It opens, inspects, and builds these containers. |
| Lua | The language of the script running inside WH3. The documented version is Lua 5.1. |
| Battle API | Functions the game exposes for reading battle state and issuing commands. |
| bm | The battle manager object used by your Lua script. |
| Unit | Usually a regiment represented by one unit card, rather than one individual soldier. |
| Bridge | The small connection carrying observations and commands between Lua and Python. |
| Harness | Your Python program managing decisions, memory, episodes, scoring, and model calls. |

RPFM edits packed game data; Lua runs inside the game. Your Python program runs alongside it. You can read existing Lua scripts without first decompiling the executable. Start with the exposed interfaces; revisit native reverse engineering only for a specific capability you cannot obtain through them. [2, 5]

Campaign and battle scripting are different environments. Code using cm, the campaign manager, is not automatically useful in a battle. Ask the coding agent to use the WH3 battle documentation and inspect your installed battle libraries. [5]

## 2 Give the coding agent and the playing agent different jobs

The coding agent builds the system. It needs the repository, documentation, RPFM, and logs. The playing agent chooses tactics. It should receive only the observations, memory, and gameplay tools defined by your experiment.

| Component | Responsibility |
| --- | --- |
| Lua battle mod | Read battle objects, manage unit controllers, execute approved orders, manage timing, and exchange files. |
| Python bridge client | Exchange messages, validate protocol fields, wait for replies, and detect timeouts. |
| Python agent loop | Assemble a prompt, call the selected model, validate its response, and submit an action batch. |
| Memory and logs | Save current plans, past actions, observations, outcomes, and reusable lessons. |
| Episode runner | Start or restart trials, record settings, detect completion, and calculate results. |

Use an API-hosted LLM first. This keeps the game and model from competing for your RTX 3060's memory and lets you debug the game integration separately from local model serving. This is a practical recommendation; the guide does not assume a particular model size will fit locally.

A local coding agent is the most convenient starting point because it can inspect game files and logs directly. If you use a cloud-only agent, give it extracted scripts and bring its changes back to the PC for testing. Cloud access alone does not provide access to a running game on your computer.

Initially, you will launch the game, select a battle, and inspect a few actions. Once the bridge and restart path are reliable, the agent can automate more of the testing.

## 3 Set up the workspace and tools

### Find the game folder

In Steam, use the game's installed-files controls to browse its installation. Call this folder GAME_ROOT in your project configuration. A typical layout is:

```text
GAME_ROOT\Warhammer3.exe
GAME_ROOT\data\
```

Do not assume your Steam library is on C:. Keep the project outside the installation, for example C:\wh3-agent. Have the coding agent create the following structure. These are proposed project paths, not game conventions.

| Project path | Purpose |
| --- | --- |
| mod_src/ | Files that will go inside your mod pack. |
| harness/ | Python code for the bridge and agent loop. |
| scenarios/ | Battle descriptions and fixed experiment settings. |
| runs/ | One directory per episode, with observations and results. |
| memory/ | Approved lessons and optional retrieval data. |
| reference/ | Locally extracted game scripts and saved API notes. |
| dist/ | Built .pack files. |
| PROJECT.md | Current goal, confirmed capabilities, and next task. |
| API_NOTES.md | Exact API signatures, sources, and in-game findings. |

Put your own source and configuration under Git. Treat extracted vanilla files as local reference material; commit the extraction recipe and file hashes. That makes game updates easier to investigate.

Have the coding agent check that Python 3 and Git are installed, create a Python virtual environment for the harness, and maintain a dependency file. You do not need to install a training framework for the first mod.

### Install and configure RPFM

Download the compiled Windows build from the author's releases page. At the time of research, the latest listed release was v5.1.1. Extract it to a tools folder and start rpfm_ui.exe. Choose the binary distribution, rather than GitHub's source-code archive. [2]

In RPFM, set Warhammer 3 as the selected game, check the game installation path, update schemas, and generate the dependencies cache. A schema describes the format of game tables; the cache helps RPFM find vanilla references. The game path should point at the installation containing the executable. [3]

The Assembly Kit is optional for the initial Lua mod. It becomes useful for additional documentation, database references, and authored maps or scenarios. If needed, install the WH3 Assembly Kit from Steam's Tools list, configure its path in RPFM, and rebuild the cache. Existing maps are sufficient for the first agent. [3]

### Connect the coding agent to RPFM

Current RPFM documents an MCP interface at:

```text
http://127.0.0.1:45127/mcp
```

MCP is a standard way to give an agent callable tools. Configure this endpoint in a local coding agent that supports Streamable HTTP MCP. RPFM can then expose pack inspection, extraction, editing, saving, and diagnostics. Its UI normally starts the backend server; the server can also run independently. [4]

Ask the agent to list the installed tools, select warhammer_3, and demonstrate that it can read one vanilla Lua file. Have it use the actual returned schemas. RPFM's UI and MCP connection have separate sessions, so do not edit the same unsaved pack in both and expect them to share changes. [4]

If MCP setup takes longer than the mod itself, use RPFM manually for the first build and let the agent edit extracted text. You can automate packaging afterward. RPFM's MCP manages files; you still need a separate bridge to control a running battle.

## 4 Make a mod that proves it loaded

The first target is one log line. This isolates packaging and loading from every other problem.

### Create the files

Have the agent create:

```text
mod_src/script/battle/mod/nt_wh3_probe.lua
mod_src/script/enable_console_logging
```

The Lua file should contain only:

```lua
out("[NT_WH3] battle probe loaded")
```

Put a short word such as enabled in the second file. Its name has no extension. The scripting documentation describes the logging switch at data/script/enable_console_logging; inside a pack, the corresponding path begins at script/. If logging fails, verify the current loader and try the documented loose-file location: GAME_ROOT\data\script\enable_console_logging. [5]

The standard battle mod directory is script/battle/mod/. CA's loader documentation and an existing WH3 battle mod demonstrate this route. Use a unique filename so your script adds behavior through the loader. You do not need to replace the default battle startup script for this first test. [6, 7]

### Build and enable the pack

In RPFM, create a new pack with type Mod and save it as nt_wh3_agent.pack. Use Add Files or Add Folder to add the contents of mod_src so the pack tree begins with script/. If you chose RPFM's MyMod workspace instead, use its import workflow. Check that you have not accidentally packed an extra mod_src directory above script/.

Install or copy the pack into GAME_ROOT\data, enable it in the game's mod manager, and restart the game. Keep other gameplay mods disabled during this initial test so failures are easy to attribute. Preserve their normal profile for regular play. [2, 7]

Enter a small single-player custom land battle on an existing open map. Find the newly written script log beside the game executable and search for [NT_WH3]. Look for names such as script_log_*.txt and select the newest battle-session log. Record the actual path; the documented destination is the directory containing the game binaries, not necessarily a folder named binaries. [5]

**Pass condition:** a fresh battle produces the marker. Ask the agent to report the pack path, its internal file tree, the log path, and the matching line.

If it fails, check the enabled pack, internal path, hidden .txt extensions, script syntax, and the newest battle log. Do not add Python or an LLM until the loading problem is understood.

### Make subsequent iteration easier

Prop Joe's Execute External Lua File mod documents running exec_battle.lua in battles with F9. It can shorten the edit-and-test loop. Verify that its filename and hotkey work in your setup before relying on it; your own packaged mod should eventually load without a development helper. [12]

## 5 Read the battle and move one unit

### First read only

Extend the probe to run at the Deployed phase, which marks the start of combat. Use the existing bm object. Have it find the player's army and enumerate its unit collection with count() and item(i). Those collections use 1-based indexes. [8, 10]

For every unit, log a stable identifier for this episode, its type, and its position. Check the count and locations against the screen. A regiment with 120 soldiers is still one unit in this enumeration.

Add health, surviving soldiers, ammunition, routing, and fatigue incrementally. The Unit API includes position(), bearing(), number_of_men_alive(), unary_hitpoints(), ammo_left(), starting_ammo(), is_routing(), and is_shattered(). Keep the last submitted order in the harness. Add engine-reported destinations and targets separately where available; these do not establish a complete observable order queue. [9]

Use your own short IDs such as friendly_01 and enemy_01, mapped to game objects within the episode. A display name is not an adequate identity. Rebuild the mapping after a restart.

### Then issue one fixed order

A unit object provides observations. A unitcontroller issues orders. Create or reuse one controller per unit when units need independent orders. Take control of one friendly infantry unit, order it to walk to a nearby reachable point, then release control. [11]

The core operations look like this. This is an API illustration, not a complete script; army, unit, and destination must already be valid.

```lua
local controller = army:create_unit_controller()
controller:add_units(unit)
controller:take_control()
controller:goto_location(destination, false)
-- Return normal control after five seconds of battle time:
bm:callback(function()
    controller:release_control()
end, 5000, "nt_wh3_release_probe")
```

The destination is a battle vector. The ground plane uses x and z; y is height. Distances are in metres. Ask the agent to label a small top-down plot and move a unit in a known direction to verify the coordinate convention. [13]

**Pass condition:** the intended unit visibly starts moving in the expected direction, the reported position changes, and human control returns. A successful function call only proves the order was issued. It does not prove arrival or tactical success.

Script control can make a player's unit card unavailable for manual orders. Returning control means returning it to its normal player or AI owner; it does not automatically turn a human army into an AI army. Keep this ownership clear so two controllers do not compete over a unit. [11]

As soon as the mod starts issuing orders, add an explicit harness_enabled flag and limit initialization to your intended single-player custom battles. The raw API provides checks for multiplayer, replays, campaign battles, and quest battles. A general battle-mod entry point should not activate your controller during unrelated play. [16]

## 6 Connect Lua to Python using a small mailbox

Use files as the first bridge. Python writes an action message; Lua reads it and returns a result. This is easy to inspect when something goes wrong.

There is useful prior art: slandau3/wh3-mcp-live includes an experimental battle bridge using external files and real callbacks. Its public implementation is a reference for communication, not a complete tactical environment. Its battle pack replaces the default battle_start.lua. Inspect and adapt the relevant pieces to your ordinary battle-mod entry point where possible, and verify compatibility with your installed version. [14]

Start with a fixed writable directory such as C:\wh3-agent\bridge. Store that path in configuration and create it before launching the game. Keep API keys in the Python process's environment.

Have the agent include a small Lua 5.1-compatible JSON encoder and decoder; JSON is not built into Lua 5.1. First test that Python and Lua can exchange a sample object. Export ordinary numbers, strings, booleans, and lists. Convert engine objects and vectors into explicit fields rather than trying to serialize them directly. [19]

### Prove the round trip without a model

1. Lua writes a hello message with a new episode ID.
2. Python reads it and sends a ping containing a request ID.
3. Lua responds with that same request ID.
4. Python requests a snapshot through the bridge.
5. Python sends the fixed movement command that already worked in Section 5.
6. Lua acknowledges it, then the next snapshot reports what happened.

Only after these work should the sender become an LLM.

### Define your own message format

Use JSON for the protocol. These fields are a proposed design for your harness, not native WH3 API fields.

```json
{
  "schema_version": 1,
  "episode_id": "trial_001",
  "request_id": "request_007",
  "based_on_observation": 7,
  "action_batch": [
    {"tool": "move", "unit_id": "friendly_02",
     "x": 25.0, "z": 40.0, "run": false}
  ]
}
```

Use one outstanding action batch at a time. Write messages to temporary files, close them, and publish them with a tested rename or ready-marker protocol. Readers must not consume half-written files. Treat Windows file locks and replacement behavior as something to test, not assume.

Track episode IDs, observation sequence numbers, and request IDs. Reject old-episode actions and actions based on an obsolete observation. Ignore duplicate request IDs or return their previous result. On restart, clear or quarantine old messages.

An acknowledgement should distinguish received, rejected, and applied. For each order, report its unit ID, request ID, application time, and any error. Later observations establish whether the requested movement or attack actually happened. Validate the batch before beginning, but do not claim the engine applies several calls atomically.

The Lua side should perform short polls and return control to the game. A blocking loop waiting for the LLM can freeze the thread needed to run the battle. Use a data parser and a fixed command dispatcher for gameplay. Arbitrary external Lua execution can be useful for development, but it gives a playing agent the ability to change the experiment itself.

## 7 Let the LLM think while the battle is paused

The initial interaction should be: observe, pause, choose orders, run a few seconds of battle time, observe again.

WH3 documents pause/resume and two timer types. A model callback is a callback on the game engine's simulation clock; it has nothing to do with calling the LLM. These callbacks stop during pause. Real callbacks follow UI updates and continue during pause. The documentation warns that battle state may be unsuitable to query from a real callback. Use real callbacks for communication and hand gameplay work back to a simulation callback. [8, 15]

### Build this state machine

1. At a model callback, capture a consistent observation and pause.
2. Publish that saved observation to Python.
3. While paused, a real callback checks for a complete action message.
4. Validate its format and IDs, store it as pending, and use a tested path to resume.
5. At the next model boundary, recheck game-dependent validity and apply the pending orders.
6. Run for a configured interval, initially five seconds of model time.
7. Capture the next observation at a model callback and pause again.

Register the simulation callback that processes pending commands before entering the first pause. The relevant documented calls are bm:repeat_callback(...), bm:repeat_real_callback(...), and bm:modify_battle_speed(0) or (1) for pause and normal speed. Verify their behavior in this small loop. [8]

This is a proposed implementation pattern. Confirm the handoff in game; there may be a small interval between resuming and applying commands. Record it instead of hiding it.

Use the engine's elapsed-time query for simulation time and Python's monotonic clock for wall time. Record requested and actual step duration. The documented time interface includes time_elapsed_ms() and model_tick_time_ms(). [16]

The documented callbacks operate at model-tick granularity, so call this pausable decision stepping. Exact frame stepping and deterministic replay remain separate capabilities to demonstrate. A five-second interval is a starting setting, not an assertion that it is tactically sufficient. [15]

### Check three failure cases early

While paused, delay Python's answer deliberately. Verify that a moving unit stops and the simulation clock does not advance; compare snapshots taken on safe boundaries before and after the wait. Confirm that the file poll still operates.

Then let Python time out. The harness should report a timeout and offer a clear local recovery action. It must not hang forever. Define separately whether benchmark timeouts count as failures or produce a fixed fallback action.

Finally, repeat with the game unfocused. Measure whether UI polling slows or stops in your setup. Keep it visible until background behavior is verified.

If the paused handoff does not work reliably, use slow motion with bounded asynchronous commands as a temporary alternative. Label those runs separately because the model's inference latency then changes the battle.

## 8 Make episodes restart reliably

For the first tests, launching a custom battle manually is acceptable. Automate restarting the same battle before trying to automate every menu and roster selection.

The battle manager documents bm:restart_battle(). Probe it after saving the episode result. Verify that the mod loads again, the expected map and roster return, deployment is handled, and a fresh ready message reaches Python. The command's existence does not establish a fast reset or restoration of every hidden state. [8]

Give reset two meanings in your code: restart the current setup, and launch a different scenario. They may need different implementations.

For each start, verify the map, army composition, deployment, difficulty, unit size, and starting health. Define what happens if deployment is still awaiting input. A reset is ready only when the new episode passes these checks and the first observation exists.

Prefer recording the actual initial state to trusting that two restarts are identical. Fix your own random seeds where applicable, but do not claim they seed the entire engine. Measure repeatability with a fixed controller on repeated starts.

Detect normal completion through the battle outcome and phase interfaces, and stop issuing orders once the result is decided. Keep win, loss, draw, time limit, crash, and user interruption separate. The raw API documents outcome queries, including victorious_alliance() and is_draw(). Validate their timing against the result screen. [16]

On completion, cancel the runner's pending step and pause callbacks, save the final observation, and allow required result-finalization phases to run. Do not pause the victory countdown while waiting for another unnecessary LLM decision. Record the final result before restarting. A victorious_alliance() result of 0 means not yet finalized; it is not a loss. [16]

Be careful with convenience victory handlers: setup_victory_callback changes the countdown behavior. A phase listener is a simpler initial choice for a logger. [8]

Later, battle setups or set-piece definitions can make scenario creation more controlled. This adds a separate authoring and launching task; existing custom battles are enough to prove the first agent. [1]

## 9 Give the first LLM player a narrow job

Use a small open-field battle. After the one-unit probe, try a generic lord, two melee units, one missile unit, and one artillery unit on each side. Cathay is a natural choice given your interest in artillery, but use whichever owned roster is convenient. Keep the initial actions focused on movement, attacking, and stopping.

Let the ordinary game AI command the opponent. Manually deploy the first few trials in a consistent formation and record that assistance. Avoid adding cavalry, spellcasting, sieges, reinforcements, and campaign effects all at once.

### Give it a compact observation

Include the battle objective, current simulation time, map bounds and coordinate convention, friendly units, enemy observations, the previous action results, and the current plan. Give units short IDs and clear roles. Include their relevant stats or a small lookup table derived from the installed game data so the model does not have to guess from lore.

Do not dump every soldier or every database field into the prompt. Start with one record per unit and add fields only when a failure shows they are needed. Unknown values should be explicit rather than silently replaced with invented numbers.

For the first integration test, it is acceptable to provide all script-visible unit positions and label the setting privileged observations. For a player-like setting, enforce visibility before information enters prompts, memory, or helper calculations.

The raw API distinguishes concealment, such as hiding in trees, from terrain line of sight. Verify a visibility filter against what the human UI reveals. A hidden unit must not leak through current positions, target pointers, distance tables, or annotations. Store last-seen information with a timestamp. [9]

### Start with four gameplay tools

| Proposed tool | Meaning |
| --- | --- |
| move | Order a named friendly unit to a ground position, optionally with facing and formation width later. |
| attack | Order a named friendly unit to attack a permitted enemy target. |
| halt | Cancel movement or orders according to the tested engine behavior. |
| keep_orders | Issue no new orders this decision; continue the previous ones. |

These are your Python/Lua wrapper names. The agent should map them to documented engine calls. Keep timing, episode resets, result calculation, and development access under the runner's control.

Validate ownership, unit existence, command type, finite coordinates, target eligibility, and battle phase. Recheck these when applying an order. Return useful errors, such as target_not_visible, rather than silently changing the target.

Ask the model for one action batch plus a short plan update. This avoids paying for a separate model call per unit and makes a decision easier to replay. Unmentioned units should keep their existing orders by default; repeatedly reissuing the same order can interrupt useful behavior.

Begin with a fixed five-second decision interval. Tune it after watching failures. A later commander mode can let the LLM choose high-level objectives while built-in AI planners handle execution, but report that as a different assistance level.

## 10 Add memory that changes decisions

Persistent memory means useful information survives the next model call or the next battle. It does not mean sending an unlimited transcript each time.

Start with plain JSON and SQLite. Given your background, this will be easier to inspect than adopting a large agent framework before the data model is clear.

| Memory | Example | Lifetime |
| --- | --- | --- |
| Current plan | Hold the centre; keep the missile unit behind friendly infantry. | One battle, updated when needed. |
| Recent observations | The left enemy unit began routing five seconds ago. | Short rolling history. |
| Last seen enemies | enemy_03 was near this hill at time 80; it is currently unseen. | One battle, explicitly uncertain. |
| Tested lessons | Moving the screen too far forward exposed the cannon in trials 12 and 17. | Across permitted learning episodes. |
| Reference knowledge | Unit role, range, movement speed, and available commands. | Versioned with the game and interface. |

Save raw episode records separately from summaries. Give each lesson links to the runs supporting it and allow correction after contradictory evidence. The model's own post-battle explanation is a hypothesis, not proof of what caused the outcome.

For evaluations, define the memory rule in advance. You might compare no memory, within-battle memory, and a fixed library of training-derived lessons. If the model learns across test battles, that is a separate online-adaptation experiment; record test order and resets.

Also preserve the coding agent's project memory in PROJECT.md and API_NOTES.md. That prevents a fresh coding session from repeating API guesses that earlier experiments already disproved.

## 11 Record enough evidence to improve the agent

For each episode, save the exact observations presented to the model, submitted actions, validation results, actual application times, next observations, final result, and model-call latency and token usage. Keep a separate evaluator state if it contains information the player was not allowed to see.

The run manifest should record game build, mod hash, code commit, scenario, roster, deployment, unit size, difficulty, observation mode, action interface, decision interval, model identifier, prompt version, and memory version. This makes a regression diagnosable after either the mod or the game changes.

Record declared outcomes independently of the LLM. A model saying it won must not determine the score. Distinguish whether a failure came from the model, the bridge, a rejected action, or the game.

### Compare against simple controllers

Start with a fixed script that attacks the nearest eligible enemy and another that holds a formation until an enemy approaches. You can inspect their logic and know whether the harness is functioning. Add a native-AI baseline when the control route is verified and a small number of your own human runs for context.

Use identical scenarios and declared assistance rules. A fixed interval, generous state access, or high-level helper can change difficulty substantially. If one player gets different tools, treat the comparison accordingly.

Track win rate, task-specific success, surviving value, invalid actions, timeouts, decisions per battle, real time, and API usage. For small pilots, report wins as a count such as 7/10 rather than implying a precise estimate. Expand trials only after the pipeline is stable.

Avoid comparing raw survivor counts across armies containing very different unit types. Choose a stated value-weighting rule and version it. Likewise, cheap ranged damage that fails to win should not become the entire reward.

### Measure the cost before planning training

A ten-minute battle with a decision every five simulation seconds needs about 120 decisions. If each decision takes ten seconds of wall time and the game runs at normal speed between decisions, that is roughly thirty minutes before loading and restart overhead. This is an arithmetic example, not a measured model latency.

Measure episodes per hour and average cost per completed episode. Lower graphics settings or resolution if needed, but keep gameplay-affecting settings such as unit size fixed within an experiment. Begin with one game instance. Parallel training workers are a later capacity decision.

## 12 Post-train only after the interface is stable

Memory, prompt changes, and training are different interventions. Memory changes what the model is told. Post-training changes its learned parameters. You can investigate the first two before choosing a training stack.

### First collect demonstrations

Record strong-model runs, fixed-script baselines, and selected decisions that you correct. Human demonstrations can use the same command tools; extracting reliable actions from mouse clicks or replays is a separate instrumentation task.

Store the precise observation, permitted memory, action, tool result, and eventual outcome. Inspect examples before training. A winning battle can contain bad individual moves, so do not automatically label every action in every win as ideal.

Reserve whole scenarios, maps, or rosters for testing. Splitting adjacent decisions from the same battle randomly across training and testing can make performance appear better because the situations are nearly identical.

### Then try supervised fine tuning

Supervised fine tuning teaches a model to produce selected actions for given observations. It is the simplest initial training question: can a smaller or cheaper model imitate useful decisions and use the tools reliably? Hugging Face TRL provides an SFTTrainer with conversational and prompt-completion data support. [17]

Choose a trainable open-weight model or a provider-supported fine-tuning target after you know the required context length and tool format. Check actual memory needs for the chosen model and training method. Schedule training separately from gameplay or use external compute if needed.

Evaluate invalid-action rate, battle outcomes, decision time, and cost. Better-looking JSON alone does not establish stronger tactics.

### Consider preference training or reinforcement learning later

Preference training uses better and worse responses to the same input. TRL's DPOTrainer supports this style of data. For your project, collect comparisons with a defensible preference label; do not call two unrelated battles a controlled comparison of two actions. [18]

Reinforcement learning can optimize rewards from fresh interactions, but it puts more pressure on reset reliability, throughput, reward quality, and repeated trials. Build a short scenario curriculum before attempting full-battle self-play. For example: protect a missile unit, hold a position, preserve artillery, then win a small mixed-army battle.

Do not expose reset, spawning, healing, teleporting, or result-writing tools to the evaluated player. Those can exist in scenario setup code, with a separate interface and event log. That distinction makes a reported win meaningful.

For a thesis, useful experiments could compare memory, decision intervals, feedback detail, or changes in the battle objective. This is a tactical-agent environment. Claims about transfer to robot control would require additional experiments.

## 13 Follow these milestones in order

| Milestone | Evidence required before moving on |
| --- | --- |
| 1 Mod loads | Fresh custom battle produces the expected log marker. |
| 2 State is readable | Friendly unit count and positions match the screen. |
| 3 Control works | One fixed order produces visible movement and control can be released. |
| 4 Bridge works | Python sends a numbered command and receives its result and next state. |
| 5 Paused stepping works | Polling survives pause, drift is measured, and repeated steps recover cleanly. |
| 6 First LLM battle | Model completes a small battle through the declared gameplay tools. |
| 7 Episodes are repeatable | Restart produces a fresh episode and reliable terminal records. |
| 8 Evaluation works | Fixed baselines and LLM runs produce comparable, inspectable results. |
| 9 Memory or training helps | A controlled comparison improves a stated metric on held-out scenarios. |

Use one milestone per coding task. Let the agent continue autonomously where it can inspect real evidence. When it needs you to interact with the game, ask for one specific action and one expected result.

Your first work session only needs to reach Milestone 1. Once that works, keep the next target equally concrete: read the army, then move one unit. The project can grow around a working loop.

## Appendix B Troubleshooting

| Symptom | Next thing to inspect |
| --- | --- |
| No startup marker | Pack enabled, correct internal path, logging switch, newest log, Lua syntax. |
| bm missing or state unavailable | Script environment and loading order; use the existing manager at a ready phase. |
| Unit count wrong | Alliance/army selection, reinforcements, collection indexing, unit-versus-soldier distinction. |
| Unit ignores the order | Ownership, phase, routing, valid target, reachability, and competing controllers. |
| Model orders the wrong regiment | Episode-local ID mapping and stale observation/request IDs. |
| Pausing prevents all commands | Mailbox is using model callbacks, or the UI timer/resume path is not functioning. |
| Game freezes during inference | Lua is blocking instead of returning to the game between short polls. |
| JSON sometimes fails | Partial publication, file locks, encoding, stale messages, parser errors. |
| Repeated strange actions after restart | Old mailbox files, old controller references, duplicated listeners, missing episode reset. |
| Pack changes seem ignored | Old installed copy, unsaved RPFM session, duplicate mods, or cached code requiring a restart. |
| Agent sees concealed enemies | Filter applied too late, cached data, target pointers, or helper calculations leaking state. |
| Training improves formatting only | Demonstration quality, reward choice, scenario diversity, and outcome evaluation. |
