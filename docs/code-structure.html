Why the loop is built this way

Use the native engine
Run the original game to preserve its simulation and outcomes. The Lua frontend drives setup and the battle mod handles orders. File exchange works across Windows and WSL. The trade-off is real startup cost and compatibility work when a game build changes. Frontend Lua · Runtime and build pin
Keep the game at 1×
Latency changes what a controller can accomplish, so the battle continues during inference. Battle time is used for order age. The harness also records wall-clock timing and checks whether game time advances at the expected rate. Timing design · Owner direction
Keep private evidence out
Lua limits live enemies to visible units. Python strips evaluation, final, setup and native before building the policy view. The lobby roster is public. Scorers can use privileged evidence after play. To test for a leak, vary only private fields and compare the rendered policy input. Policy projection · Boundary check
Match the right request
The normal play loop keeps one request outstanding. Job and battle IDs reject foreign commands, and request ties each acknowledgement to its batch. based_on names the harness snapshot for that batch. For a team order, read source_seq and source_ms to find the member’s actual input and measure its age. A Python validation failure is recorded and the loop sends an empty batch. An engine refusal is recorded separately. Mailbox contract · Team source in the replay · Validation and errors

Controller design

Decide what the model controls, what code handles, and how long a decision stays useful.

One harness, several controllers

The factory makes a fresh controller per battle. decide reads the policy view, acknowledge receives feedback for its request, and metadata describes the decision or controller. The harness owns the mailbox. The same seam supports baselines, models and imported controllers. Controller contract and factory

Scripted baselines
hold shows what the engine does on its own. rush_nearest asks how far a simple, reactive rule gets. A scripted witness serves a different purpose: it demonstrates that a particular scenario can be solved. Baselines
Direct model
llm_rules gives the model the interface and objective and asks for orders. A blocking API call leaves those orders based on an older snapshot while the battle advances. Prompt tips, provider, reasoning effort and memory all change the system being compared. Direct policy · Rules prompt · Rendered inputs
Planner and executor
commander asks the model asynchronously for standing assignments. skills turns them into orders from fresh observations. This keeps local reactions quick and gives the model a longer decision horizon. The skill library bounds what the planner can express. Compare against skills alone to estimate what the planner adds. Planner · Executor
Graph-based control
A configured graph runs named nodes and transitions as conditions change. A model can write a validated graph before play, shifting some computation outside the battle. The live goal-model variant proposes a target preference while the graph keeps running. The graph’s branches are inspectable and bound what the controller can do. Account for authoring cost separately from play cost. Graph authoring · Composition · Graph runtime · Live target preferences

Benchmark and evidence

A battle measures an entire controller under a particular setup, observation budget and clock. Each stronger claim needs a comparison that isolates it.

From scenario to result

  1. Declare the task

    Freeze the roster, setup, disclosed objective and controller configuration.

    Scenario files · Setup and readback
  2. Check the task

    A witness tries to solve it. Simple foils test whether a shortcut also works.

    Cannae witness · Task design
  3. Run the plan

    Record assignments and dispositions. Keep fresh launches distinct from rematches.

    Plans · Suite · Queue
  4. Read the evidence

    Use engine endings and independent readings. Retain incomplete trials and missing evidence.

    Outcome and rank · Report
Define the denominator
The profile win rate uses qualifying engine wins, losses and draws, including engine timer endings. An interruption during the final copy can exclude a recorded ending. A wall cap or provider stop without an engine ending stays unresolved. Controller forfeits also stay visible outside the rate. Show attempted counts and what missing outcomes could change. Outcome rules · Owner decisions and open accounting choices
Use valid proxies
The profile ranks engine outcome first and uses terminal unit condition where available. Scenario readings answer narrower questions. In Escalade, contact comes from the engine’s melee flag on a living unit. Distance alone can count troops on opposite sides of a wall. Escalade readings · Accepted-order reader
Design the comparison
For a communication ablation, hold scenario, model, skill code, ownership and observation scope fixed while changing the message path. Report any coupled changes. To compare independent win rates, the repo has Fisher’s exact test and a Newcombe interval for the difference. For matched win/non-win outcomes, exact McNemar uses pairs where only one arm won. Ticks, calls and rematches within a launch are poor substitutes for independent trials. Small-sample statistics · Proposed analysis rules

What the Cannae pilot showed

The November 11 exploratory Cannae pilot ran six fresh launches, two each for peer, relay and overview. All six lost. These are unverified development results. They expose failure modes and leave architecture ranking unresolved. Debug the model replies, local refusals and engine rejections separately, then ask whether the task and endpoint discriminate between controllers. Pilot, exact conditions and failure audit

Reset, replay and data

Reuse a starting state for a controlled comparison or reuse a saved decision for offline analysis.

Branch from a battle checkpoint

  1. Save the prefix

    Capture setup and inputs in a native replay, plus the Lua seed.

  2. Rebuild the state

    Replay inputs, checking tick checksums on the way.

  3. Hand over at 1×

    Replace replay input with live input and try the next order.

The agreed Land check compares two same-order restores to one source and requires a changed-order restore to diverge. At 210e356, each same-order restore matched 2,000 planned tick checksums and all nine required live readings. The changed-order branch first diverged at tick 1303. Native checksums can miss field construction, so live readings matter too. Wall-clock timers and other setups limit the conclusion. In-game restore · Agreed Land harness · Pass and scope

Keep records useful after the run

Replay and adjudicate
The job’s manifest.json records source hashes, configuration and prompt provenance. Per battle, trace.jsonl ties decisions to requests, private.jsonl holds evaluator capture when enabled, and result.json records the ending and summaries. Link accepted orders to later engine events before crediting execution. An absent enemy in a public replay can be out of view. Capture · Replay reader
Export decisions
For supported built-in model controllers, the exporter groups a model request and its attempts into a row with available execution links. It preserves recorded prompts, flags missing fields, and inventories excluded episodes such as configured teams. Supervised fine-tuning requires a completed reply with recorded prompts. A valid reply can still be poor training data. Split by scenario or checkpoint family to reduce leakage across near-duplicate decisions. Exporter · SFT builder · Trace contract
Study a fixed choice
The checkpoint research uses an offline contextual bandit: show a battle state, choose one of a fixed set of candidate orders, and read a reward for that branch. With rewards tabulated for all available actions, the update can optimize the sum of each action’s probability times its reward without sampling actions from the game. Held-out checkpoints and shuffled action order help detect memorization and slot bias. The first synthetic experiment collapsed to a single action. The prototype is paused. Offline performance leaves live generalization and multi-step credit assignment open. Bandit and adapter code · Prototype results and limits

The light factory

An experimental workflow for agent-written changes. The owner sets requirements and decides what counts as verification. Agents implement, run checks and surface decisions that affect interpretation.

From a request to a repeatable check

  1. Write a change card

    Name the behavior, independent requirement and wrong implementation the check should catch.

    Card
  2. Isolate the change

    Use an editing worktree. Keep game jobs on a stable checkout and report choices that change meaning.

    Worktrees · Judgement markers
  3. Challenge the check

    Show the clean version passes and a plausible wrong version fails. The reviewer gets the card, diff and raw results.

    Planted defects · Reviewer
  4. Gate and record

    Run Ruff and the offline suite. Save the output and hash the checked tree for the commit hook.

    Gate · Commit hook · CI
Why test the tests?
A check can pass while missing the defect it was written for. --plants replays known bad changes. refusal_sweep.py removes one guard at a time to find untested refusals. One plant adds army-wide magic to a captain’s input. The test compares the full model request to catch that leak. The tools count a timeout as caught, so inspect the failure before calling it a good regression. Refusal sweep · Checks of checks
What counts as verification?
Tests cover the cases they exercise. The agreed-check register records the method and supported revision for a stronger claim. A passing parser test can prove malformed input was rejected in that case. Proving a unit acted needs engine evidence. A marker preserves open choices such as which failures enter a benchmark denominator. Agreed checks · Review and independent recount
Where can it fail?
The ordinary gate is offline, risky edits are warnings, and concurrent edits can prevent a pass record. The hook checks that the tree still matches the pass. Reviewer judgments can also miss faults, so the project tests reviewers on prior bugs and clean diffs. Gate limits · Early factory experiment

Questions to practice

An order was accepted and the unit stood still. Where do you debug?

Match the acknowledgement to the decision by request. Measure age from the snapshot that produced the order, using the member’s source timestamp for a team decision. Look for the intended effect in later engine observations. Check intervening orders, target visibility, unit state and terrain. For a coding exercise, sketch a test where a late acknowledgement for request A arrives while B is outstanding. B must remain outstanding. Trace · Request matching

What is the state, and what does the policy actually observe?

The engine owns the state. Fog of war and observation delay make the policy’s input partial. The policy can use history to infer where a unit might be, but an unseen enemy’s true current position belongs only to the engine. Issued orders can keep running while the agent waits. For a formal model, specify what an observation contains, when actions take effect and how you track elapsed time. Observation boundary

If you double the call rate, will the agent react faster?

Measure throughput and observation age separately. More calls can finish per second while each still uses stale state. Hold the controller fixed and inject observation delay to probe sensitivity, or compare a slow planner plus fast executor against direct control and report the changed action abstraction. Use the battle clock for age, wall time for provider latency. Controller designs · Latency study

How would you show communication helped?

Specify the endpoint first. Compare a message-enabled controller with a matched muted control, verify that messages reached the intended prompts, and record cost, failure rate and order age. Freeze a development candidate, reserve held-out variants, and report the effect with uncertainty by the independent replicate unit. A transcript shows delivery. A controlled change can support a causal claim. Benchmark and pilot

How would an optimizing policy game this reward?

If rewarded for getting close to an enemy, it could approach across a wall without engaging. Use engine contact or the task’s actual outcome, and run a shortcut controller that gets close without achieving the objective. Keep shaping rewards and final evaluation separate. Vary the setup and check that valid alternate solutions still succeed. Contact reading · Shortcut checks

How would you turn these traces into trustworthy training data?

Recover the original prompt, mark each attempt, join orders to application and check subsequent effects. Keep missing evidence explicit. Freeze splits by scenario or checkpoint family before sampling or relabeling. Audit a sample against the raw trace and a domain expert, report rejection rates, and use independent held-out play to assess an adapter. Export and learning

What would an offline bandit win prove?

Compare against a fixed-choice baseline and a simple public-state heuristic. Test on held-out checkpoint families with action slots shuffled and use the table’s best available reward as an upper reference. A result can show state-dependent choice within those candidates. To generalize to live play, first check branch execution, then test fresh setups. A multi-step policy additionally changes the states it later encounters and has to assign credit across orders. Reset check · Offline objective

How would you turn this into a repeatable eval service?

Version each task’s setup, public instruction, controller and grader. Use a fresh launch or a checked restore, enforce a cap, retain every disposition and retry only under a predeclared rule. Put outcome evidence outside the policy view. Pilot witness and shortcut runs before paying for scale. Compared with Harbor’s containerized task pattern, WH3 adds native Windows game startup, timing and licence dependencies that constrain throughput. WH3 runbook · Terminal-Bench paper

What did you own, and how did you catch agent mistakes?

Give a real example. For checkpoints, the owner allowed a faster rebuild before handover, required 1× play afterwards, and agreed to a same-orders check with a changed-order control. Point to the recorded pass and explain its limits. For a code change, show a card, a failure the reviewer or planted test exposed, and how the result is tied to the checked revision. Checkpoint evidence · Light factory
