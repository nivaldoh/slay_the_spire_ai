src/twwarhammer3/__main__.py

Start in main()

Open src/twwarhammer3/__main__.py at the bottom. The source links point to the exact lines in the implementation at aecdd84. The recorded battle used an earlier revision, b7e2dd1.

  1. Let Python resolve the package

    __main__.py:601

    uv run --locked starts Python in the project environment. With -m twwarhammer3, Python executes src/twwarhammer3/__main__.py. At the bottom of that file raise SystemExit(main()) calls the entry point. The tokens beginning with play are its command-line arguments.

  2. Parse the tokens and choose a handler

    __main__.py:595 · __main__.py:41

    build_parser() registers play as a subcommand. parse_args() reads the arguments into an argparse.Namespace. Here args.command is "play", args.episodes is the integer 1, and args.output is a Path. Looking up COMMANDS["play"] gives the function run_play in this same file.

    parser = build_parser()
args = parser.parse_args()
return COMMANDS[args.command](args, parser)

  3. Turn the parsed arguments into a job

    __main__.py:443 · controllers/factory.py:171 · policy_names.py:6

    The CLI’s run_play(args, parser) copies the options into config, keeping the command name and output directory out of that dictionary. It fills in the default model and the paths to the ledger and results register. rotation(config) checks the requested combinations of policy and delay.

    Inside factories(config), policy_parts() splits the policy string into llm_rules, the model z-ai/glm-5.3 and the reasoning effort low. The factory reads configs/twwarhammer3/rules_prompt.md and stores a constructor in makers under the full policy string. The job will call that constructor once per battle.

    Now step into the last call in the CLI handler. The import from twwarhammer3.battle.play import play as run_play gives the battle runner the same name as the handler. This call crosses into battle/play.py.

    manifest = run_play(args.output, config, makers=makers)

Interview practice

What is the environment’s state, and what is an observation?

The engine tracks both armies, visibility and ongoing actions. A snapshot exposes only part of that state and takes time to reach the controller. The model can use history to estimate where a hidden unit went. Issued orders can continue executing between decisions.

How would you make a repeatable eval out of this setup?

Freeze the scenario, public instruction, controller and grader before running. Check the lobby, start a fresh launch or a tested restore, cap spending, and keep a record for every planned attempt. Run a witness and a shortcut control before scaling. Native Windows startup and the real-time clock constrain throughput.

battle/play.py · _drive()

Step through one iteration of _drive()

Mailbox.wait_new_battle() gives the loop its first battle ID and sequence number. Inside while True, wait_observation(battle=…, after_seq=…) waits for a newer snapshot. Python and Lua run independently. The two processes exchange observations and orders through files.

Who gets to see what?

The controller, during play
Own units, visible enemies and the public lobby roster. A hidden enemy’s last known location can inform a guess about where it went.
The evaluator, after play
The saved ending and, when captured, private frames with hidden units. Feeding these into a model prompt would give the model information a player lacks.
What changes when a different controller takes the Knights?

The same battle loop calls decide(view) on a fresh policy and returns feedback through acknowledge(). The harness owns the mailbox. Each policy gets a different way to spend its thinking time.

Scripted rule
hold leaves units alone. rush_nearest reacts to visible enemies. These baselines reveal how far simple behavior gets.
Direct model
llm_rules asks for orders on each decision. The Knights’ run used this approach. A slow answer can be legal against its input even after the battlefield has changed.
Planner and skills
An asynchronous model assigns longer-lived tasks. Scripted skills execute on fresh observations. Compare with skills alone to estimate the planner’s contribution.
Graph policy
A model can author a graph before play. Named actions and transitions let the runtime react without asking for every move. Its vocabulary limits what the plan can express.
Team
Workers reason about assigned regiments while one dispatcher sends orders. A member’s source_ms identifies the view it actually used. A recent dispatch can carry an old decision.

Interview practice

An order was accepted and the unit stood still. Where do you debug?

Match the decision and acknowledgement by request. Check which snapshot the policy saw, whether the target was still visible, and whether a later order superseded this one. Look for movement or combat in subsequent engine readings. A useful regression presents a late acknowledgement for A while B is pending and checks that B is still pending.

How would you extract just the accepted orders from the trace?

Index decisions by request ID. For each acknowledgement with an application time, look up that request and each successful result’s one-based index into its batch. Test a mixed batch, an unknown request and index zero, which could otherwise select the last order in Python.

Would doubling the call rate make the cavalry react sooner?

Calls per second measure throughput. Reaction also depends on how old each observation is when the order reaches the game. Compare source and application times on the battle clock. Hold the controller fixed and vary injected observation delay to test sensitivity. A slow planner with a fast executor changes the action interface too.

How those records enter a benchmark comparison

  1. Keep the endingThe episode result records how this battle ended. The trace lets a reader work backward to particular decisions.runs/…/episode-0000/
  2. Apply one outcome ruleThe benchmark profile counts qualifying engine wins, losses and draws. If the provider stops during play and the game supplies no ending, that attempt stays unresolved.benchmarks/profile.py
  3. Show the denominatorStart from the planned attempts, including absent results. Report how many started, finished and entered the win rate.benchmarks/plans.py · results/

A benchmark adds a repeatable task and comparison to this loop. A scripted witness tries an intended solution. Simple controls try shortcuts. A scenario’s evaluator reads recorded behavior independently of the witness, so another controller can earn credit for a different solution.

A separate experiment asked whether captains could coordinate one army

In the Cannae pilot, the captains each owned regiments and saw local contacts. Peer captains could message one another. Relay captains wrote to a commander who depended on reports for new sightings. Overview gave that commander army-wide information. Peer versus relay changes both the route and the worker count.

Each design lost both fresh launches. Those six development battles left the designs unranked. The traces supported a narrower investigation. Some captains tried to order regiments they did not own. The next request omitted the reason their reply had failed.

Researchers retried each of 40 saved successor prompts twice, once unchanged and once with the rejection explained. The parser accepted 39 of 40 unchanged replies and 35 of 40 with feedback. These prompts were selected after failures in the same six battles. A legal reply can contain no orders, and live recovery remains unverified.

Interview practice

A batch has one win, a timer draw and a provider stop. What is its win rate?

Assume the provider stopped during play with no ending, and the two engine endings are complete. The profile counts one win in two battles (50%) and reports one unresolved attempt. Across all three attempts, the possible win rate ranges from one-third to two-thirds. Those bounds describe the missing outcome. Sampling uncertainty is a separate question.

How would you isolate the value of captain-to-captain messages?

Compare the same captains with messages delivered or muted. Hold the model, local views, ownership, skill code and scenario fixed. Check the exact recipient prompts and report order age, costs and failures. Declare the endpoint and independent trial unit in advance. For matched binary outcomes, the pairs where only one arm won carry the evidence for a difference.

How could a controller game a score for engaging the enemy?

A distance reward can be high for units separated by a wall. Escalade reads the engine’s melee flag on a living unit. Try a shortcut controller that approaches without engaging, and a valid alternative strategy that should still succeed. Keep any training reward distinct from the final evaluation.

Benchmark accounting and scope

Forfeits remain visible outside the profile win rate. An interrupted final copy can exclude even a recorded engine ending. The benchmark tracks the engine outcome first and uses terminal unit condition where available. Owner decisions and open choices · Outcome mapping

Try a different order or learn from the record

To ask what another move would have done, you need a comparable starting state. To teach a model to choose a move, you need the input and target for that decision. The project has separate tools for these two uses.

Branch the simulation
Capture a replay prefix and Lua seed, rebuild the battle and switch to live input at 1×. Check that the same orders reproduce the state and that a changed order can make the branch diverge.
Build a training example
For supported model controllers, export a request and its attempts. Keep a nonempty, completed final reply with both prompts and no recorded error on the decision or final attempt. The final user prompt may contain retry feedback that the first prompt lacked.

Interview practice

Which trace rows would make trustworthy training examples?

Keep the actual prompt and reply from the same attempt. Inspect execution evidence and retain missing fields explicitly. A legal order can be tactically poor. Audit labels against raw traces, hold out whole scenario or checkpoint families to limit leakage, and assess the trained policy on fresh play.

What can the offline checkpoint learner actually learn?

At a checkpoint, a contextual bandit chooses one of a fixed set of candidate orders. With a reward for each candidate, the first method maximizes J = Σ π(a|s) r(s,a). Under softmax its derivative with respect to a logit is π(a|s)[r(s,a) − J]. A later objective averages log J, weighting each case’s gradient by 1/J when J is positive. Compare with a fixed-action baseline, shuffle display slots and test held-out checkpoint families. The first synthetic method collapsed to one action. Learning which candidate works in a table leaves multi-step credit assignment and live strength open. The prototype is paused.
